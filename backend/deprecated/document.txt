# GraphQL API Documentation for Real-Time Communication Platform  

## Background Context and Documentation Purpose  

This documentation serves as the comprehensive integration guide for frontend developers building against a real-time communication backend powered by GraphQL. The system implements a complete social messaging platform with four interconnected core systems: user authentication with session management, bidirectional friend relationships, feature-rich messaging with advanced capabilities (replies, reactions, editing, forwarding), and WebRTC-based audio/video calling with full signaling support.  

### Architectural Context  

The backend employs a hybrid architecture combining PostgreSQL for relational user and friendship data, MongoDB for document-based conversations and messages, and Redis for session storage, call state management, and rate limiting. The GraphQL layer unifies these data sources through a single endpoint for queries/mutations and a WebSocket endpoint for real-time subscriptions using the `graphql-transport-ws` protocol.  

### Authentication Model  

The API uses **session-based authentication** with HTTP-only cookies (`connect.sid`), stored in Redis with configurable TTL (default 7 days). All requests requiring authentication must include `credentials: 'include'` in fetch options to ensure cookies are sent cross-origin. Subscriptions authenticate via the same cookie mechanism during WebSocket handshake. There is no JWT or token-based authentication—session cookies are the sole authentication mechanism.  

### Data Consistency Patterns  

The system maintains eventual consistency between SQL and NoSQL stores. Friend relationships stored in PostgreSQL gate access to messaging features in MongoDB. Conversation participants are validated against friendship status. Call state lives temporarily in Redis (2-hour TTL) and persists to MongoDB only upon call completion/rejection/miss as message metadata.  

### Custom Scalar Types  

- **DateTime**: ISO 8601 string format (`2024-01-15T10:30:00.000Z`). All timestamps serialize to this format. When parsing, the scalar accepts ISO strings and converts them to Date objects internally.  
- **JSON**: Arbitrary JSON objects/arrays. Used for SDP payloads, ICE candidates, and read status maps. No schema validation—accepts any valid JSON structure.  

### Error Code Taxonomy  

GraphQL errors follow a standardized `extensions.code` pattern:  

- **UNAUTHENTICATED**: No valid session exists (req.session.userId is null/undefined). Returned when accessing protected resolvers without login.  
- **FORBIDDEN**: Authenticated but lacking permission (e.g., trying to accept someone else's friend request, accessing conversations you're not participant in).  
- **BAD_REQUEST**: Input validation failure (malformed IDs, empty content, invalid cursor format, out-of-range reaction types).  
- **NOT_FOUND**: Resource doesn't exist in database (conversation, message, friend request, call not found).  
- **INTERNAL_SERVER_ERROR**: Unexpected server failure (database connection issues, Redis unavailability). In production, error messages are sanitized.  

### Subscription Architecture  

All subscriptions use PubSub (GraphQL Subscriptions library) with in-memory event emitters. When multiple backend instances run (horizontally scaled), a shared Redis PubSub adapter would be required (not currently implemented—single-instance assumption). Subscriptions filter events server-side using `withFilter` to ensure users only receive events they're authorized to see.

## 1. Overview  

### Endpoints  

- **GraphQL HTTP Endpoint**: `http://localhost:4000/graphql` (queries and mutations)  
- **GraphQL WebSocket Endpoint**: `ws://localhost:4000/graphql` (subscriptions)  
- **Protocol**: `graphql-transport-ws` (graphql-ws library compatible)  

### Authentication Mechanism  

Session-based authentication using HTTP-only cookies. The server sets a `connect.sid` cookie upon successful login, stored in Redis with default 7-day expiration (configurable via `SESSION_MAX_AGE` environment variable).  

**Required HTTP Headers for All Requests:**  

```javascript  
fetch('http://localhost:4000/graphql', {  
  method: 'POST',  
  credentials: 'include', // CRITICAL: Ensures cookies are sent  
  headers: {  
    'Content-Type': 'application/json'  
  },  
  body: JSON.stringify({ query, variables })  
})  
```  

**Cookie Behavior:**  
- **Set on**: Successful `login` mutation  
- **Cleared on**: `logout` mutation  
- **Validated on**: Every authenticated resolver checks `req.session.userId`  
- **WebSocket Auth**: Cookie parsed from `Sec-WebSocket-Protocol` handshake headers  

### Custom Scalar Types  

#### DateTime  

**Serialization**: JavaScript `Date` objects serialize to ISO 8601 strings.  

```json  
{  
  "timeSent": "2024-01-15T14:30:00.000Z"  
}  
```  

**Parsing**: Accepts ISO 8601 strings. Frontend should pass timestamps as strings in queries/mutations.  

#### JSON  

**Format**: Any valid JSON value (object, array, string, number, boolean, null).  

**Usage Examples:**  
- SDP offers/answers: `{ type: "offer", sdp: "v=0\r\no=..." }`  
- ICE candidates: `{ candidate: "candidate:1 1 UDP...", sdpMLineIndex: 0 }`  
- Read status maps: `{ "user123": "2024-01-15T10:00:00Z", "user456": "2024-01-15T10:05:00Z" }`  

### Error Code Taxonomy  

| Code | Meaning | Common Causes |  
|------|---------|---------------|  
| `UNAUTHENTICATED` | No valid session | Accessing protected resolver without login, session expired |  
| `FORBIDDEN` | Insufficient permissions | Accepting others' friend requests, accessing non-participant conversations |  
| `BAD_REQUEST` | Invalid input | Empty message content, invalid ObjectId format, cursor parse failure |  
| `NOT_FOUND` | Resource doesn't exist | Message/conversation/call not found in database |  
| `INTERNAL_SERVER_ERROR` | Server error | Database connection failure, Redis unavailable |

## 2. Authentication System  

All authentication mutations are **public** (no session required). Queries like `me` require authentication.  

### Registration  

**Signature:**  
```graphql  
mutation Register($username: String!, $password: String!): AuthResponse!  
```  

**Input Validation Rules:**  
- **Username**:   
  - Minimum 3 characters  
  - Alphanumeric + underscore only (`/^[a-zA-Z0-9_]+$/`)  
  - Trimmed of whitespace  
- **Password**:   
  - Minimum 8 characters  
  - No character restrictions (hashed with bcrypt)  

**Success Response Structure:**  
```typescript  
{  
  success: boolean  
  message: string  
  user: {  
    id: string  
    username: string  
  } | null  
}  
```  

**Example Request:**  
```graphql  
mutation {  
  register(username: "alice_smith", password: "SecurePass123") {  
    success  
    message  
    user {  
      id  
      username  
    }  
  }  
}  
```  

**Success Response:**  
```json  
{  
  "data": {  
    "register": {  
      "success": true,  
      "message": "Registration successful! Please log in.",  
      "user": {  
        "id": "123",  
        "username": "alice_smith"  
      }  
    }  
  }  
}  
```  

**Error Scenarios:**  

1. **Username too short:**  
```json  
{  
  "data": {  
    "register": {  
      "success": false,  
      "message": "Username must be at least 3 characters",  
      "user": null  
    }  
  }  
}  
```  

2. **Invalid characters:**  
```json  
{  
  "data": {  
    "register": {  
      "success": false,  
      "message": "Username can only contain letters, numbers, and underscores",  
      "user": null  
    }  
  }  
}  
```  

3. **Duplicate username:**  
```json  
{  
  "data": {  
    "register": {  
      "success": false,  
      "message": "Username already exists",  
      "user": null  
    }  
  }  
}  
```

### Login  

**Signature:**  
```graphql  
mutation Login($username: String!, $password: String!): AuthResponse!  
```  

**Session Creation Behavior:**  
1. Validates credentials against PostgreSQL `users` table  
2. Regenerates session ID (security best practice)  
3. Sets `req.session.userId` to authenticated user ID  
4. Saves session to Redis with TTL  
5. Sets `connect.sid` HTTP-only cookie in response  

**Cookie Handling Requirements:**  
- Frontend **must** include `credentials: 'include'` in all subsequent requests  
- Cookie persists across browser sessions (unless cleared)  
- Cookie path: `/` (available to all routes)  
- `sameSite: 'lax'` (allows cross-site GET requests, prevents CSRF on POST)  

**Example Request:**  
```graphql  
mutation {  
  login(username: "alice_smith", password: "SecurePass123") {  
    success  
    message  
    user {  
      id  
      username  
    }  
  }  
}  
```  

**Success Response:**  
```json  
{  
  "data": {  
    "login": {  
      "success": true,  
      "message": "Login successful",  
      "user": {  
        "id": "123",  
        "username": "alice_smith"  
      }  
    }  
  }  
}  
```  

**Error Response (Invalid Credentials):**  
```json  
{  
  "data": {  
    "login": {  
      "success": false,  
      "message": "Invalid credentials",  
      "user": null  
    }  
  }  
}  
```  

**Post-Login Requirements:**  
After successful login, the frontend should:  
1. Store user data in application state  
2. Redirect to main application view  
3. Establish WebSocket connection for subscriptions (uses same cookie)  

---  

### Logout  

**Signature:**  
```graphql  
mutation Logout: LogoutResponse!  
```  

**Session Destruction Behavior:**  
1. Destroys session in Redis (via `req.session.destroy()`)  
2. Clears `connect.sid` cookie with `res.clearCookie()`  
3. Returns success even if no session existed (idempotent)  

**Example Request:**  
```graphql  
mutation {  
  logout {  
    success  
    message  
  }  
}  
```  

**Response:**  
```json  
{  
  "data": {  
    "logout": {  
      "success": true,  
      "message": "Logged out successfully"  
    }  
  }  
}  
```  

**Post-Logout Actions:**  
Frontend should:  
1. Clear application state (user data, messages, etc.)  
2. Close WebSocket connection  
3. Redirect to login page

### Current User Query  

**Signature:**  
```graphql  
query Me: ProtectedDataResponse!  
```  

**Authentication Requirement:** **Required** (throws `UNAUTHENTICATED` if no session)  

**Returns:**  
- User ID and username from session  
- Timestamp of query execution  
- Welcome message  

**Example Request:**  
```graphql  
query {  
  me {  
    message  
    user {  
      id  
      username  
    }  
    timestamp  
  }  
}  
```  

**Success Response:**  
```json  
{  
  "data": {  
    "me": {  
      "message": "Welcome back, alice_smith!",  
      "user": {  
        "id": "123",  
        "username": "alice_smith"  
      },  
      "timestamp": "2024-01-15T14:30:00.000Z"  
    }  
  }  
}  
```  

**Error When Unauthenticated:**  
```json  
{  
  "errors": [  
    {  
      "message": "Not authenticated",  
      "extensions": {  
        "code": "UNAUTHENTICATED"  
      }  
    }  
  ],  
  "data": null  
}  
```  

**Usage Pattern:**  
Call `me` query on app initialization to:  
1. Verify session validity  
2. Retrieve current user data  
3. Handle session expiration gracefully (redirect to login on `UNAUTHENTICATED`)

## 3. Friend Management System  

All friend operations require authentication. Friendships are **bidirectional**—when user A adds user B as friend, both can see each other in friends lists.  

### Queries

**Signature:**  
```graphql

```  

**Description:** Retrieves authenticated user's friends list with full user objects.  

**Authentication:** **Required**  

**Example Request:**

```graphql  
      createdAt

        id  
        username

}  
```  

**Response:**

## 4. Messaging System  

Messaging requires both authentication and conversation participation. All operations validate that the authenticated user is a participant in the target conversation.  

### Queries  

#### fetchMessages  

**Signature:**  
```graphql  
query FetchMessages(  
  $conversationId: ID!  
  $cursor: String  
  $limit: Int = 20  
): MessageConnection!  
```  

**Description:** Retrieves message history with cursor-based pagination. Messages return in **descending** time order (newest first for initial load, then older messages when paginating).  

**Cursor Format:** Base64-encoded ISO 8601 timestamp. Example:  
```javascript  
// Encoding cursor  
const cursor = Buffer.from('2024-01-15T14:30:00.000Z').toString('base64');  
// "MjAyNC0wMS0xNVQxNDozMDowMC4wMDBa"  

// Decoding cursor (backend does this)  
const timestamp = Buffer.from(cursor, 'base64').toString('utf-8');  
// "2024-01-15T14:30:00.000Z"  
```  

**Pagination Parameters:**  
- **cursor**: Timestamp cursor from previous response's `endCursor`. Omit for first page.  
- **limit**: Number of messages to fetch. Default: 20, Max: 100 (enforced server-side).  

**hasNextPage Usage:**  
- `true`: More messages exist before `endCursor` timestamp  
- `false`: No older messages available  

**Authentication:** **Required**  
**Authorization:** Must be conversation participant.  

**Example Initial Load:**  
```graphql  
query {  
  fetchMessages(conversationId: "conv123", limit: 20) {  
    edges {  
      cursor  
      node {  
        id  
        conversationId  
        senderId  
        recipientId  
        content  
        timeSent  
        meta {  
          isUnsent  
          isForwarded  
          replyTo  
          lastEditAt  
        }  
        reactions {  
          userId  
          type  
        }  
        repliedMessage {  
          id  
          content  
          senderId  
        }  
      }  
    }  
    pageInfo {  
      hasNextPage  
      endCursor  
    }  
  }
```  

### Message Object Structure  

#### repliedMessage Nested Loading  

The `repliedMessage` field uses **DataLoader** to batch-load original messages when `meta.replyTo` is set. This prevents N+1 query issues when fetching conversation history with replies.  

**Example:**  
```graphql  
query {  
  fetchMessages(conversationId: "conv123") {  
    edges {  
      node {  
        id  
        content  
        meta {  
          replyTo  
        }  
        repliedMessage {  
          id  
          content  
          senderId  
          # ⚠️ Cannot nest repliedMessage further (no recursive replies)  
        }  
      }  
    }  
  }  
}  
```  

**Unsent Original Messages:**  
If replied-to message is unsent, `repliedMessage.content` returns `null`:  
```json  
{  
  "repliedMessage": {  
    "id": "msg123",  
    "content": null,  // ← Original was unsent  
    "senderId": "456"  
  }  
}  
```

#### Meta Field Mappings (snake_case to camelCase)  

Database stores fields in `snake_case`, GraphQL returns `camelCase`:  

| Database Field | GraphQL Field | Type | Description |  
|----------------|---------------|------|-------------|  
| `is_unsent` | `isUnsent` | Boolean | Message was unsent by sender |  
| `is_forwarded` | `isForwarded` | Boolean | Message was forwarded from another conversation |  
| `reply_to` | `replyTo` | ID (nullable) | ID of message being replied to |  
| `last_edit_at` | `lastEditAt` | DateTime (nullable) | Timestamp of last edit |  

**Default Meta Values:**  
```json

    "isUnsent": false,  
    "isForwarded": false,  
    "replyTo": null,  
    "lastEditAt": null  
  }  
}
```  

## 5. WebRTC Calling System  

WebRTC calling uses Redis for ephemeral call state (2-hour TTL) and MongoDB for call history persistence. Only friends can call each other.  

### Enums  

#### CallType  

```graphql  
enum CallType {  
  voice   # Audio only  
  video   # Audio + video  
  screen  # Screen sharing  
}  
```  

**Usage:** Passed to `initiateCall` mutation.  

#### CallStatus  

```graphql  
enum CallStatus {  
  initiating  # Call being created (brief state)  
  ringing     # Waiting for recipient to answer  
  active      # Call in progress (answered)  
  ended       # Call ended normally  
  missed      # Call never answered (ringing → ended without answer)  
  rejected    # Recipient explicitly rejected call  
}  
```  

**State Transitions:**  
- `initiating` → `ringing` (automatic after creation)  
- `ringing` → `active` (via `answerCall`)  
- `ringing` → `rejected` (via `rejectCall`)  
- `ringing` → `missed` (via `endCall` before answer)  
- `active` → `ended` (via `endCall` after answer)  

---  

### Mutations  

#### initiateCall  

**Signature:**  
```graphql  
mutation InitiateCall(  
  $recipientId: ID!  
  $callType: CallType!  
): CallInitiationResponse!  
```  

**Validation:**  
1. Cannot call self  
2. Recipient must exist  
3. Must be friends with recipient (checks PostgreSQL)  

**Behavior:**  
1. Generates UUID for call ID  
2. Stores call state in Redis with 2-hour TTL  
3. Transitions `initiating` → `ringing`  
4. Triggers `incomingCall` subscription for recipient  
5. Returns STUN server configuration  

**STUN Servers Provided:**

- `stun:stun1.l.google.com:19302`

**Example Request:**

```graphql  
    message

      id  
      participantIds  
      type  
      status  
      startTime  
    }  
    stunServers {  
      urls  
    }  
  }  
}  
```

#### answerCall  

**Signature:**  
```graphql  
mutation AnswerCall($callId: ID!): CallInitiationResponse!  
```  

**Description:** Transitions call from `ringing` to `active` state. Only recipient can answer.  

**Authorization:** Must be the recipient (second participant in `participantIds` array).  

**Behavior:**  
1. Validates call exists in Redis  
2. Validates current user is recipient (`participantIds[1]`)  
3. Validates call status is `ringing`  
4. Sets `answerTime` timestamp  
5. Transitions to `active` status  
6. Triggers `callStateChanged` subscription for both participants  
7. Returns STUN servers for WebRTC negotiation  

**Authentication:** **Required**  

**Example Request:**  
```graphql

    success  
    message  
    call {  
      id  
      participantIds  
      type  
      status  
      startTime  
    }  
    stunServers {  
      urls  
    }  
  }  
}  
```  

**Success Response:**  
```json  
{  
  "data": {  
    "answerCall": {  
      "success": true,  
      "message": "Call answered",  
      "call": {  
        "id": "call-uuid-123",  
        "participantIds": ["123", "456"],  
        "type": "video",  
        "status": "active",  
        "startTime": "2024-01-15T14:30:00.000Z"  
      },  
      "stunServers": {  
        "urls": [  
          "stun:stun.l.google.com:19302",  
          "stun:stun1.l.google.com:19302"  
        ]  
      }  
    }  
  }  
}  
```  

**Error Scenarios:**  

1. **Call not found/expired:**  
```json  
{  
  "data": {  
    "answerCall": {  
      "success": false,  
      "message": "Call not found or expired",  
      "call": null,  
      "stunServers": null  
    }  
  }  
}  
```  

2. **Not recipient:**  
```json  
{  
  "data": {  
    "answerCall": {  
      "success": false,  
      "message": "Unauthorized to answer this call",  
      "call": null,  
      "stunServers": null  
    }  
  }  
}  
```  

3. **Wrong status:**  
```json

      "success": false,  
      "message": "Cannot answer call in ended state",  
      "call": null,

  }

```

#### rejectCall  

**Signature:**  
```graphql

```  

**Description:** Explicitly rejects incoming call. Available to either participant.  

**Behavior:**  
1. Validates call exists in Redis  
2. Validates user is a participant  
3. Sets status to `rejected`  
4. Saves call to MongoDB call history (no duration)  
5. Deletes call from Redis  
6. Triggers `callStateChanged` subscription  

**Authentication:** **Required**  
**Authorization:** Must be call participant.  

**Example Request:**  
```graphql

}
```  

**Success Response:**  
```json  
{  
  "data": {  
    "rejectCall": true  
  }  
}  
```  

**Error Response:**  
```json  
{  
  "errors": [  
    {  
      "message": "Call not found",  
      "extensions": {  
        "code": "NOT_FOUND"  
      }  
    }  
  ],  
  "data": null  
}  
```  

**Usage Pattern:**  
Recipient uses this when declining incoming call. Initiator can also reject before recipient answers (cancel call).

#### endCall  

**Signature:**  
```graphql  
mutation EndCall($callId: ID!): Boolean!  
```  

**Description:** Ends active call or marks ringing call as missed. Calculates duration if call was answered.  

**Behavior:**  
1. Validates call exists and user is participant  
2. Calculates duration if status is `active` (endTime - answerTime)  
3. Sets status to `missed` if status was `ringing`, otherwise `ended`  
4. Saves call to MongoDB as message with `call_metadata`  
5. Deletes call from Redis  
6. Triggers `callStateChanged` subscription  

**Call History Message Structure:**  
```javascript  
{  
  conversation_id: ObjectId,  
  sender_id: initiatorId,  
  recipient_id: recipientId,  
  content: "VIDEO call",  // or "VOICE call", "SCREEN call"  
  time_sent: startTime,  
  call_metadata: {  
    type: "video",  
    duration: 125,  // seconds (null if never answered)  
    status: "completed",  // or "missed"  
    initiated_by: initiatorId  
  }  
}  
```  

**Authentication:** **Required**  
**Authorization:** Must be call participant.  

**Example Request:**  
```graphql  
mutation {  
  endCall(callId: "call-uuid-123")  
}  
```  

**Success Response:**  
```json  
{  
  "data": {  
    "endCall": true  
  }  
}  
```  

**Error Scenarios:**  
Same as `rejectCall` (NOT_FOUND, FORBIDDEN).  

**Usage Pattern:**  
Either participant calls this to terminate call. Frontend should:  
1. Close peer connection  
2. Stop media streams  
3. Call `endCall` mutation  
4. Clean up UI state

#### callSignal  

**Signature:**  
```graphql  
subscription CallSignal($callId: ID!): CallSignal!  
```  

**Description:** Receives SDP offers/answers and ICE candidates from other peer. Filtered to exclude sender.  

**Return Type:**  
```graphql  
type CallSignal {  
  callId: ID!  
  senderId: String!  
  type: String!  # "offer", "answer", "ice-candidate"  
  payload: JSON!  
}  
```  

**Filtering:**  
- Only the **other peer** receives signals (sender does not receive own signals)  
- Both participants must be in the call  
- Call must exist in Redis  

**Signal Routing:**  
- Initiator sends offer → Recipient receives it  
- Recipient sends answer → Initiator receives it  
- Both send ICE candidates → Other peer receives them  

**Authentication:** **Required**  

**Example Subscription:**  
```graphql  
subscription {  
  callSignal(callId: "call-uuid-123") {  
    callId  
    senderId  
    type  
    payload  
  }  
}  
```  

**Event Payloads:**  

**SDP Offer:**  
```json  
{  
  "data": {  
    "callSignal": {  
      "callId": "call-uuid-123",  
      "senderId": "123",  
      "type": "offer",  
      "payload": {  
        "type": "offer",  
        "sdp": "v=0\r\no=- 1234567890 2 IN IP4 127.0.0.1\r\n..."  
      }  
    }  
  }  
}  
```  

**SDP Answer:**  
```json  
{  
  "data": {  
    "callSignal": {  
      "callId": "call-uuid-123",  
      "senderId": "456",  
      "type": "answer",  
      "payload": {  
        "type": "answer",  
        "sdp": "v=0\r\no=- 9876543210 2 IN IP4 127.0.0.1\r\n..."  
      }  
    }  
  }  
}  
```  

**ICE Candidate:**  
```json  
{  
  "data": {  
    "callSignal": {  
      "callId": "call-uuid-123",  
      "senderId": "456",  
      "type": "ice-candidate",  
      "payload": {  
        "candidate": "candidate:842163049 1 udp 1677729535 203.0.113.45 54321 typ srflx",  
        "sdpMLineIndex": 0,  
        "sdpMid": "0"  
      }  
    }  
  }  
}  
```  

**Frontend Integration:**  
```javascript  
const signalSubscription = client.subscribe({  
  query: gql`  
    subscription CallSignal($callId: ID!) {  
      callSignal(callId: $callId) {  
        senderId  
        type  
        payload  
      }  
    }  
  `,  
  variables: { callId }  
});  

signalSubscription.subscribe({  
  next: async ({ data }) => {  
    const { type, payload } = data.callSignal;  
    
    if (type === 'offer') {  
      // Recipient receives offer  
      await peerConnection.setRemoteDescription(payload);  
      const answer = await peerConnection.createAnswer();  
      await peerConnection.setLocalDescription(answer);  
      await sendSDPAnswerMutation({ callId, sdp: answer });  
      
    } else if (type === 'answer') {  
      // Initiator receives answer  
      await peerConnection.setRemoteDescription(payload);  
      
    } else if (type === 'ice-candidate') {  
      // Both receive ICE candidates  
      const candidate = new RTCIceCandidate(payload);  
      await peerConnection.addIceCandidate(candidate);  
    }  
  }  
});  
```

#### callStateChanged  

**Signature:**  
```graphql  
subscription CallStateChanged($callId: ID!): CallStateChange!  
```  

**Description:** Fires on call state transitions (ringing → active, active → ended, etc.). Both participants receive this.  

**Return Type:**  
```graphql  
type CallStateChange {  
  callId: ID!  
  status: CallStatus!  
  timestamp: DateTime!  
}  
```  

**Trigger Conditions:**  
- `answerCall` → `active` status  
- `rejectCall` → `rejected` status  
- `endCall` → `ended` or `missed` status  

**Filtering:**  
- Both participants receive state changes  
- Must be call participant  

**Authentication:** **Required**  

**Example Subscription:**  
```graphql  
subscription {  
  callStateChanged(callId: "call-uuid-123") {  
    callId  
    status  
    timestamp  
  }  
}  
```  

**Event Payloads:**  

**Call Answered:**  
```json  
{  
  "data": {  
    "callStateChanged": {  
      "callId": "call-uuid-123",  
      "status": "active",  
      "timestamp": "2024-01-15T14:30:15.000Z"  
    }  
  }  
}  
```  

**Call Rejected:**  
```json  
{  
  "data": {  
    "callStateChanged": {  
      "callId": "call-uuid-123",  
      "status": "rejected",  
      "timestamp": "2024-01-15T14:30:10.000Z"  
    }  
  }  
}  
```  

**Call Ended:**  
```json  
{  
  "data": {  
    "callStateChanged": {  
      "callId": "call-uuid-123",  
      "status": "ended",  
      "timestamp": "2024-01-15T14:35:00.000Z"  
    }  
  }  
}  
```  

**Frontend Integration:**  
```javascript  
const stateSubscription = client.subscribe({  
  query: gql`  
    subscription CallStateChanged($callId: ID!) {  
      callStateChanged(callId: $callId) {  
        status  
        timestamp  
      }  
    }  
  `,  
  variables: { callId }  
});  

stateSubscription.subscribe({  
  next: ({ data }) => {  
    const { status } = data.callStateChanged;  
    
    if (status === 'active') {  
      // Call connected  
      hideRingingUI();  
      showActiveCallUI();  
      startCallTimer();  
      
    } else if (status === 'rejected') {  
      // Call was rejected  
      stopRingtone();  
      showNotification('Call rejected');  
      cleanupCall();  
      
    } else if (status === 'ended' || status === 'missed') {  
      // Call ended  
      stopCallTimer();  
      closePeerConnection();  
      showCallEndedUI();  
    }  
  }  
});  
```

### Complete WebRTC Flow Diagram  

```mermaid  
sequenceDiagram  
    participant A as Initiator (Alice)  
    participant S as GraphQL Server  
    participant R as Recipient (Bob)  
    participant Redis as Redis  
    participant Mongo as MongoDB  

    Note over A,Mongo: Call Setup Phase  
    
    A->>S: mutation initiateCall(recipientId: Bob, callType: video)  
    S->>Redis: Store call state (TTL: 2h)  
    S->>R: subscription incomingCall → { call, caller }  
    S-->>A: { success: true, call, stunServers }  
    
    Note over R: Bob receives incoming call notification  
    R->>R: Show incoming call UI  
    R->>S: mutation answerCall(callId)  
    S->>Redis: Update call status → "active"  
    S->>A: subscription callStateChanged → { status: "active" }  
    S->>R: subscription callStateChanged → { status: "active" }  
    S-->>R: { success: true, call, stunServers }  
    
    Note over A,R: WebRTC Negotiation Phase  
    
    A->>A: Create RTCPeerConnection  
    A->>A: addTrack(localStream)  
    A->>A: createOffer()  
    A->>S: mutation sendSDPOffer(callId, sdp)  
    S->>R: subscription callSignal → { type: "offer", payload: SDP }  
    
    R->>R: setRemoteDescription(offer)  
    R->>R: createAnswer()  
    R->>S: mutation sendSDPAnswer(callId, sdp)  
    S->>A: subscription callSignal → { type: "answer", payload: SDP }  
    
    A->>A: setRemoteDescription(answer)  
    
    Note over A,R: ICE Candidate Exchange (Trickle)  
    
    par Alice sends candidates  
        A->>S: mutation sendICECandidate(candidate1)  
        S->>R: subscription callSignal → { type: "ice-candidate" }  
        A->>S: mutation sendICECandidate(candidate2)  
        S->>R: subscription callSignal → { type: "ice-candidate" }  
    and Bob sends candidates  
        R->>S: mutation sendICECandidate(candidate1)  
        S->>A: subscription callSignal → { type: "ice-candidate" }  
        R->>S: mutation sendICECandidate(candidate2)  
        S->>A: subscription callSignal → { type: "ice-candidate" }  
    end  
    
    Note over A,R: Connection Established - Media Flows via WebRTC (P2P)  
    
    Note over A,R: Active Call (duration tracked)  
    
    Note over A,R: Call Termination Phase  
    
    A->>A: User clicks "End Call"  
    A->>A: Close RTCPeerConnection  
    A->>S: mutation endCall(callId)  
    S->>Redis: Get call data, calculate duration  
    S->>Mongo: Save call history as Message with call_metadata  
    S->>Redis: Delete call state  
    S->>A: subscription callStateChanged → { status: "ended" }  
    S->>R: subscription callStateChanged → { status: "ended" }  
    S-->>A: true  
    
    R->>R: Close RTCPeerConnection  
    R->>R: Clean up UI  
```  

**Key Flow Points:**  

1. **Initiator Flow:**  
   - Call `initiateCall` → Get `callId` and `stunServers`  
   - Create `RTCPeerConnection` with STUN servers  
   - Subscribe to `callSignal` and `callStateChanged`  
   - Wait for `active` state via subscription  
   - Generate SDP offer → `sendSDPOffer`  
   - Listen for SDP answer via `callSignal` subscription  
   - Send ICE candidates as discovered  
   - Receive remote ICE candidates and add to peer connection  
   - When ending: `endCall` mutation  

2. **Recipient Flow:**  
   - Subscribe to `incomingCall` (persistent subscription)  
   - Receive notification → Show incoming call UI  
   - User accepts → `answerCall` mutation  
   - Create `RTCPeerConnection` with returned STUN servers  
   - Subscribe to `callSignal` and `callStateChanged`  
   - Receive SDP offer via `callSignal` subscription  
   - Generate SDP answer → `sendSDPAnswer`  
   - Send ICE candidates as discovered  
   - Receive remote ICE candidates and add to peer connection  
   - When ending: `endCall` mutation  

3. **Rejection Flow:**  
   - Recipient calls `rejectCall` instead of `answerCall`  
   - Both participants receive `callStateChanged` → `rejected`  
   - Call saved to history with no duration  

4. **Missed Call Flow:**  
   - Initiator calls `endCall` while status is still `ringing`  
   - Backend sets status to `missed`  
   - Saved to history with `status: "missed"` and no duration

### Call Persistence: Redis vs MongoDB Strategy  

**Redis (Ephemeral State):**  
- **Purpose:** Active call state management  
- **TTL:** 2 hours (7200 seconds)  
- **Data Stored:**  
  ```javascript  
  {  
    id: "uuid",  
    participantIds: ["user1", "user2"],  
    type: "video",  
    status: "active",  
    startTime: "2024-01-15T14:30:00.000Z",  
    answerTime: "2024-01-15T14:30:15.000Z"  // Set when answered  
  }  
  ```  
- **Lifecycle:**  
  - Created on `initiateCall`  
  - Updated on `answerCall` (adds `answerTime`, status → `active`)  
  - Deleted on `endCall` or `rejectCall`  
  - Auto-expires after 2 hours if not cleaned up (safety net)  

**MongoDB (Persistent History):**  
- **Purpose:** Call history and conversation timeline  
- **Storage Location:** `messages` collection with `call_metadata` field  
- **Data Stored:**  
  ```javascript  
  {  
    _id: ObjectId,  
    conversation_id: ObjectId,  
    sender_id: "initiatorUserId",  
    recipient_id: "recipientUserId",  
    content: "VIDEO call",  // or "VOICE call", "SCREEN call"  
    time_sent: startTime,  
    meta: {  
      is_unsent: false,  
      is_forwarded: false,  
      reply_to: null,  
      last_edit_at: null  
    },  
    reactions: [],  
    call_metadata: {  
      type: "video",  
      duration: 125,  // seconds (null if never answered)  
      status: "completed",  // or "missed", "rejected"  
      initiated_by: "initiatorUserId"  
    }  
  }  
  ```  
- **Lifecycle:**  
  - Created on `endCall` or `rejectCall`  
  - Appears in conversation message history  
  - Frontend can display call entries in chat timeline  
  - Never deleted (permanent history)  

**Why This Strategy:**  
1. **Performance:** Redis provides fast read/write for signaling lookups  
2. **Scalability:** Active calls are small dataset; completed calls in MongoDB  
3. **Separation:** Real-time state vs historical data  
4. **TTL Safety:** Abandoned calls auto-clean from Redis  
5. **Conversation Integration:** Call history appears as special message type in chat  

**Frontend Pattern for Call History:**  
```javascript  
// Fetch messages with call metadata  
const { data } = await fetchMessages({ conversationId });  

data.fetchMessages.edges.forEach(({ node: msg }) => {  
  if (msg.call_metadata) {  
    // Render call entry  
    renderCallHistoryEntry({  
      type: msg.call_metadata.type,  
      duration: msg.call_metadata.duration,  
      status: msg.call_metadata.status,  
      timestamp: msg.timeSent,  
      initiatedBy: msg.call_metadata.initiated_by  
    });  
  } else {  
    // Render regular message  
    renderMessage(msg);  
  }  
});  
```

## 6. Subscription Connection Guide  

### WebSocket Endpoint and Protocol  

**Endpoint:** `ws://localhost:4000/graphql` (same path as HTTP, different protocol)  

**Protocol:** `graphql-transport-ws` (modern WebSocket protocol)  
- Supersedes legacy `subscriptions-transport-ws`  
- Supported by `graphql-ws` npm package  
- Better error handling and connection lifecycle management  
- Apollo Client v3+ compatible  

**Subprotocol Negotiation:**  
Server supports both `graphql-transport-ws` and `graphql-ws` subprotocols via WebSocket handshake.  

---  

### Cookie-Based Authentication for Subscriptions  

**How It Works:**  
1. User logs in via HTTP `login` mutation → Server sets `connect.sid` cookie  
2. Frontend establishes WebSocket connection → Browser automatically includes cookies in handshake  
3. Server extracts `connect.sid` from `Cookie` header during WebSocket `onConnect`  
4. Server looks up session in Redis  
5. If valid, attaches `user` object to subscription context  
6. All subscriptions have access to authenticated user via `context.user`  

**Important:** Cookies are sent automatically by the browser—**no additional headers needed** in WebSocket connection.  

**Cookie Handling Differences:**  
- **HTTP Requests:** Use `credentials: 'include'` in fetch options  
- **WebSocket:** Browser handles cookies automatically (same-origin or CORS with proper configuration)

```javascript  
  },
```  

### Handling Connection Drops and Reconnection  

**Common Causes:**  
- Network interruption  
- Server restart  
- Session expiration  
- Browser tab backgrounded (mobile)  

**Apollo Client Auto-Reconnection:**  
Apollo Client's `GraphQLWsLink` automatically handles reconnection with exponential backoff. No additional configuration needed.  

**Manual Reconnection Handling:**  
```javascript  
const wsClient = createClient({  
  url: 'ws://localhost:4000/graphql',  
  
  // Retry connection on close  
  retryAttempts: 5,  
  retryWait: async (retryCount) => {  
    await new Promise(resolve => setTimeout(resolve, Math.min(1000 * 2 ** retryCount, 10000)));  
  },  
  
  // Handle connection events  
  on: {  
    connected: () => console.log('WebSocket connected'),  
    closed: (event) => console.log('WebSocket closed', event),  
    error: (error) => console.error('WebSocket error', error),  
  },  
  
  // Session validation  
  connectionParams: async () => {  
    // Check if session is still valid before reconnecting  
    const response = await fetch('http://localhost:4000/graphql', {  
      method: 'POST',  
      credentials: 'include',  
      headers: { 'Content-Type': 'application/json' },  
      body: JSON.stringify({ query: '{ me { id } }' }),  
    });  
    
    const { errors } = await response.json();  
    if (errors) {  
      // Session expired—redirect to login  
      window.location.href = '/login';  
      throw new Error('Session expired');  
    }  
    
    return {};  // Cookies sent automatically  
  },  
});  
```  

**Subscription Lifecycle Management:**  
```javascript  
import { useEffect } from 'react';  
import { useSubscription } from '@apollo/client';  

function ChatComponent({ conversationId }) {  
  const { data, error } = useSubscription(MESSAGE_RECEIVED, {  
    variables: { conversationId },  
    shouldResubscribe: true,  // Resubscribe on connection restore  
  });  

  useEffect(() => {  
    // Component mounted—subscription started  
    console.log('Subscribed to messages');  
    
    return () => {  
      // Component unmounted—subscription automatically cleaned up  
      console.log('Unsubscribed from messages');  
    };  
  }, [conversationId]);  

  if (error) {  
    if (error.message.includes('UNAUTHENTICATED')) {  
      // Session expired during subscription  
      window.location.href = '/login';  
    }  
    return <div>Error: {error.message}</div>;  
  }  

  return <div>{/* Chat UI */}</div>;  
}  
```  

**Best Practices:**  
1. **Subscribe on Mount:** Start subscriptions when component mounts  
2. **Unsubscribe on Unmount:** Clean up to prevent memory leaks  
3. **Handle UNAUTHENTICATED Errors:** Redirect to login if session expired  
4. **Debounce Resubscriptions:** Avoid rapid subscribe/unsubscribe cycles  
5. **Global Connection Status:** Show "Connecting..." UI during reconnection

## 8. Error Handling Guide  

### Error Response Structure  

GraphQL errors follow this format:  
```json  
{  
  "errors": [  
    {  
      "message": "Human-readable error message",  
      "locations": [{ "line": 2, "column": 3 }],  
      "path": ["mutationName", "fieldName"],  
      "extensions": {  
        "code": "ERROR_CODE"  
      }  
    }  
  ],  
  "data": null  
}  
```  

**Key Fields:**  
- `message`: Error description  
- `extensions.code`: Machine-readable error code  
- `path`: GraphQL path where error occurred  
- `data`: `null` for errors, or partial data if some fields succeeded  

---  

### Extension Codes and Meanings  

#### UNAUTHENTICATED  

**Meaning:** No valid session exists  

**Common Causes:**  
- Accessing protected resolver without logging in  
- Session expired (exceeded TTL)  
- Session cookie not sent (`credentials: 'include'` missing)  
- Session destroyed via logout  

**Example:**  
```json  
{  
  "errors": [  
    {  
      "message": "Not authenticated",  
      "extensions": {  
        "code": "UNAUTHENTICATED"  
      }  
    }  
  ],  
  "data": null  
}  
```  

**Frontend Handling:**  
```javascript  
if (error.graphQLErrors.some(e => e.extensions?.code === 'UNAUTHENTICATED')) {  
  // Redirect to login  
  window.location.href = '/login';  
}  
```  

---  

#### FORBIDDEN  

**Meaning:** Authenticated but lacking permission  

**Common Causes:**  
- Accessing resources you don't own (other user's messages)  
- Not a conversation participant  
- Trying to accept someone else's friend request  
- Answering call you're not recipient of  

**Example:**  
```json  
{  
  "errors": [  
    {  
      "message": "You are not a participant in this conversation",  
      "extensions": {  
        "code": "FORBIDDEN"  
      }  
    }  
  ],  
  "data": null  
}  
```  

**Frontend Handling:**  
```javascript  
if (error.graphQLErrors.some(e => e.extensions?.code === 'FORBIDDEN')) {  
  // Show error message  
  showNotification('You do not have permission to perform this action', 'error');  
}  
```  

---  

#### BAD_REQUEST  

**Meaning:** Input validation failure  

**Common Causes:**  
- Empty message content  
- Username too short (<3 chars)  
- Invalid character in username  
- Malformed MongoDB ObjectId  
- Invalid cursor format  
- Reaction type out of range (not 1-6)  
- Message content exceeds 5000 characters  

**Examples:**  

**Empty Content:**  
```json  
{  
  "errors": [  
    {  
      "message": "Message content cannot be empty",  
      "extensions": {  
        "code": "BAD_REQUEST"  
      }  
    }  
  ],  
  "data": null  
}  
```  

**Invalid ID:**  
```json  
{  
  "errors": [  
    {  
      "message": "Invalid conversation ID format",  
      "extensions": {  
        "code": "BAD_REQUEST"  
      }  
    }  
  ],  
  "data": null  
}  
```  

**Frontend Handling:**  
```javascript  
if (error.graphQLErrors.some(e => e.extensions?.code === 'BAD_REQUEST')) {  
  // Show validation error to user  
  const message = error.graphQLErrors[0].message;  
  showFieldError(fieldName, message);  
}  
```

**Meaning:** Resource doesn't exist in database  

**Common Causes:**  
- Conversation ID doesn't exist  
- Message ID not found  
- Friend request ID invalid  
- Call ID expired/deleted  
- User ID doesn't exist  

**Example:**  

### Global Error Handler Pattern  

```javascript  
function handleGraphQLError(error) {  
  // Network error (server unreachable)  
  if (error.networkError) {  
    showNotification('Unable to connect to server. Check your connection.', 'error');  
    return;  
  }  

  // GraphQL errors  
  if (error.graphQLErrors && error.graphQLErrors.length > 0) {  
    error.graphQLErrors.forEach(err => {  
      const code = err.extensions?.code;  
      const message = err.message;  

      switch (code) {  
        case 'UNAUTHENTICATED':  
          // Redirect to login  
          localStorage.clear();  
          window.location.href = '/login';  
          break;  

        case 'FORBIDDEN':  
          showNotification(`Permission denied: ${message}`, 'error');  
          break;  

        case 'BAD_REQUEST':  
          showNotification(`Invalid input: ${message}`, 'warning');  
          break;  

        case 'NOT_FOUND':  
          showNotification(`Not found: ${message}`, 'info');  
          break;  

        case 'INTERNAL_SERVER_ERROR':  
          showNotification('Server error. Please try again later.', 'error');  
          logErrorToMonitoring(err);  // Send to error tracking service  
          break;  

        default:  
          showNotification(message, 'error');  
      }  
    });  
  }  
}  

// Apollo Client usage  
const client = new ApolloClient({  
  // ...  
  onError: handleGraphQLError,  
});  
```

```graphql

```  

### Messaging Flow  
```graphql  
# Create conversation  
mutation { createConversation(participantId: "456") { id participantIds createdAt } }  

# Send message

# Fetch messages (initial load)  
query { fetchMessages(conversationId: "conv123", limit: 20) { edges { node { id content timeSent } cursor } pageInfo { hasNextPage endCursor } } }  

# Fetch more messages (pagination)

```  

### Call Flow

```graphql  
# Send ICE candidate  
mutation { sendICECandidate(callId: "call-uuid-123", candidate: { candidate: "...", sdpMLineIndex: 0, sdpMid: "0" }) }  

# End call  
mutation { endCall(callId: "call-uuid-123") }
```  

## Performance Optimization Tips  

### 1. Message Pagination  
- Start with `limit: 20` for initial load  
- Increase to `limit: 50` for "Load More" actions  
- Cache cursors to avoid re-fetching same messages  
- Implement virtual scrolling for large conversations  

### 2. Subscription Management  
- Subscribe only to active conversation  
- Unsubscribe when navigating away  
- Use single WebSocket connection for all subscriptions  
- Debounce typing indicator sends (300ms recommended)  

### 3. DataLoader Benefits  
- `repliedMessage` field uses DataLoader (batches queries)  
- Fetch multiple messages with replies in single query  
- No N+1 problem when loading conversation history  

### 4. Rate Limiting Awareness  
- `updateLastOnline`: 60-second throttle  
- Call `setTyping(false)` after 3 seconds of inactivity  
- Batch read receipts (mark as read once per conversation view)  

### 5. Caching Strategy  
```javascript  
// Apollo Client cache configuration  
const cache = new InMemoryCache({  
  typePolicies: {  
    Query: {  
      fields: {  
        fetchMessages: {  
          keyArgs: ['conversationId'],  
          merge(existing = { edges: [] }, incoming) {  
            return {  
              ...incoming,  
              edges: [...existing.edges, ...incoming.edges]  
            };  
          }  
        }  
      }  
    },  
    Message: {  
      fields: {  
        reactions: {  
          merge: false // Replace, don't merge  
        }  
      }  
    }  
  }  
});  
```

## Security Considerations  

### 1. Cookie Handling  
- Always use `credentials: 'include'` for HTTP requests  
- Ensure `sameSite: 'lax'` is set on cookies (server-side)  
- Use HTTPS in production for secure cookies  

### 2. Input Validation  
- Sanitize user input before sending (strip HTML, check length)  
- Validate IDs are valid formats before mutations  
- Handle long messages (5000 char limit server-side)  

### 3. Error Exposure  
- Production errors sanitized (`INTERNAL_SERVER_ERROR` details hidden)  
- Log errors to monitoring service (Sentry, LogRocket, etc.)  
- Don't display raw error messages to users  

### 4. WebRTC Security  
- STUN servers are public (Google's servers provided)  
- For production, add TURN servers for NAT traversal  
- Validate all signaling messages  
- Implement call encryption (DTLS-SRTP enabled by default in WebRTC)

## Troubleshooting Guide  

### Common Issues  

**Issue: Cookies not being sent**  
```javascript  
// ❌ Wrong  
fetch('/graphql', { body: query })  

// ✅ Correct  
fetch('/graphql', {   
  credentials: 'include',  // Critical!  
  body: query   
})  
```  

**Issue: Subscription not receiving events**  
- Check user is conversation participant  
- Verify WebSocket connection is established  
- Check browser console for connection errors  
- Ensure subscription variables match mutation variables (same conversationId)  

**Issue: Messages not loading past first page**  
- Validate cursor is base64-encoded ISO 8601 string  
- Check `hasNextPage` is true before requesting more  
- Ensure `endCursor` is passed to next query  

**Issue: Call not connecting**  
- Verify both users are friends  
- Check STUN server connectivity (test with STUN checker tool)  
- Ensure ICE candidates are being exchanged  
- Check firewall/NAT settings (may need TURN servers)  

**Issue: "UNAUTHENTICATED" error after some time**  
- Session expired (default 7 days)  
- Redirect to login and clear local state  
- Implement token refresh logic if needed

## Summary of Key Points  

1. **Authentication:** Session-based with HTTP-only cookies, `credentials: 'include'` required  
2. **Pagination:** Cursor-based using base64-encoded ISO 8601 timestamps  
3. **Real-time:** WebSocket subscriptions with automatic reconnection  
4. **WebRTC:** Signaling via GraphQL, media via P2P with STUN servers  
5. **Error Handling:** Standardized codes (UNAUTHENTICATED, FORBIDDEN, BAD_REQUEST, NOT_FOUND, INTERNAL_SERVER_ERROR)  
6. **Authorization:** Conversation participants, friend relationships, message ownership  
7. **Rate Limiting:** 60-second throttle on `updateLastOnline`  
8. **Data Storage:** Redis (sessions, calls), PostgreSQL (users, friends), MongoDB (messages, conversations)  

This documentation provides everything needed to implement a fully-functional real-time messaging and calling frontend without examining backend code. All operations, types, errors, and patterns are comprehensively documented with examples.
