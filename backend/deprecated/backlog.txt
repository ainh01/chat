[CHAT-001] Create Conversation
───────────────────────────────────────────────────────────────────────
GraphQL Schema:
  type Mutation {
    createConversation(participantId: String!): Conversation!
  }
  
  type Conversation {
    id: ID!
    participantIds: [String!]!
    lastMessage: LastMessagePreview
    readStatus: JSON
    createdAt: DateTime!
  }

Authentication:
  - Required: userId from context (cookie session)
  - Validates: userId exists in SQL users table

MongoDB Operations:
  1. Check if conversation already exists:
     db.conversations.findOne({ 
       participant_ids: { $all: [userId, participantId] } 
     })
     
  2. If not exists, create:
     db.conversations.insertOne({
       participant_ids: [userId, participantId].sort(),
       last_message: null,
       read_status: {},
       created_at: new Date(),
       is_blocked: false
     })

Business Logic:
  - participantId ≠ userId (can't chat with self)
  - participantId must exist in SQL users table
  - participant_ids stored alphabetically sorted for consistent lookups
  - Return existing conversation if already created (idempotent)

Error Handling:
  - 401: User not authenticated
  - 400: Invalid participantId (not found in SQL)
  - 400: participantId === userId

Acceptance Criteria:
  ✓ Creates new conversation between two users
  ✓ Returns existing conversation if already exists
  ✓ Rejects invalid participant IDs
  ✓ Stores participant_ids in sorted order

Index Required:
  db.conversations.createIndex({ participant_ids: 1 })

[CHAT-002] Send Message
───────────────────────────────────────────────────────────────────────
GraphQL Schema:
  type Mutation {
    sendMessage(
      conversationId: ID!
      content: String!
    ): Message!
  }
  
  type Message {
    id: ID!
    conversationId: ID!
    senderId: String!
    recipientId: String!
    content: String!
    timeSent: DateTime!
    meta: MessageMeta!
    reactions: [Reaction!]!
  }
  
  type MessageMeta {
    isUnsent: Boolean!
    isForwarded: Boolean!
    replyTo: ID
    lastEditAt: DateTime
  }

Authentication:
  - Required: userId from context
  - Validates: userId is participant in conversationId

MongoDB Operations:
  1. Verify conversation exists and user is participant:
     const conv = await db.conversations.findOne({
       _id: ObjectId(conversationId),
       participant_ids: userId
     })
     if (!conv) throw new Error("Unauthorized or conversation not found")
     
  2. Determine recipientId:
     const recipientId = conv.participant_ids.find(id => id !== userId)
     
  3. Insert message:
     const msg = await db.messages.insertOne({
       conversation_id: ObjectId(conversationId),
       sender_id: userId,
       recipient_id: recipientId,
       content: content.trim(),
       time_sent: new Date(),
       meta: {
         is_unsent: false,
         is_forwarded: false,
         reply_to: null,
         last_edit_at: null
       },
       reactions: []
     })
     
  4. Update conversation's last_message (denormalization):
     await db.conversations.updateOne(
       { _id: ObjectId(conversationId) },
       { $set: {
         last_message: {
           sender_id: userId,
           text: content.substring(0, 100), // Preview only
           time_sent: new Date()
         }
       }}
     )

WebSocket Event:
  - Publish to: `MESSAGE_SENT:${conversationId}`
  - Payload: Complete Message object
  - Subscribers: Both participants (see CHAT-004)

Business Logic:
  - content must be non-empty after trim
  - Max length: 5000 characters
  - recipientId auto-determined from conversation participants

Error Handling:
  - 401: User not authenticated
  - 403: User not participant in conversation
  - 400: Empty content or exceeds max length
  - 404: Conversation not found

Acceptance Criteria:
  ✓ Saves message to messages collection
  ✓ Updates conversations.last_message cache
  ✓ Broadcasts message via WebSocket to both participants
  ✓ Rejects non-participants
  ✓ Trims whitespace and validates length

Index Required:
  db.messages.createIndex({ conversation_id: 1, time_sent: -1 })

[CHAT-003] Fetch Messages (with Lazy Loading)
───────────────────────────────────────────────────────────────────────
GraphQL Schema:
  type Query {
    fetchMessages(
      conversationId: ID!
      cursor: String
      limit: Int = 20
    ): MessageConnection!
  }
  
  type MessageConnection {
    edges: [MessageEdge!]!
    pageInfo: PageInfo!
  }
  
  type MessageEdge {
    cursor: String!
    node: Message!
  }
  
  type PageInfo {
    hasNextPage: Boolean!
    endCursor: String
  }

Authentication:
  - Required: userId from context
  - Validates: userId is participant in conversationId

MongoDB Operations:
  1. Verify user is participant:
     const conv = await db.conversations.findOne({
       _id: ObjectId(conversationId),
       participant_ids: userId
     })
     
  2. Decode cursor (if provided):
     const cursorDate = cursor ? new Date(Buffer.from(cursor, 'base64').toString()) : new Date()
     
  3. Fetch messages (cursor-based pagination):
     const messages = await db.messages.find({
       conversation_id: ObjectId(conversationId),
       time_sent: { $lt: cursorDate }
     })
     .sort({ time_sent: -1 })
     .limit(limit + 1) // Fetch one extra to check hasNextPage
     .toArray()
     
  4. Build response:
     const hasNextPage = messages.length > limit
     const edges = messages.slice(0, limit).map(msg => ({
       cursor: Buffer.from(msg.time_sent.toISOString()).toString('base64'),
       node: msg
     }))

Business Logic:
  - Returns newest messages first (DESC order)
  - Cursor encodes time_sent as base64 timestamp
  - limit capped at max 100
  - Fetch all messages including unsent. In resolver, if `meta.is_unsent`, set content = `null` (frontend displays placeholder).

Error Handling:
  - 401: User not authenticated
  - 403: User not participant in conversation
  - 400: Invalid cursor format
  - 400: limit out of range (1-100)

Acceptance Criteria:
  ✓ Returns paginated messages sorted newest first
  ✓ Cursor-based pagination works correctly
  ✓ hasNextPage accurately indicates more messages
  ✓ Respects meta.is_unsent (content hidden in resolver)
  ✓ Rejects non-participants

Performance:
  - Index on (conversation_id, time_sent) prevents full scan
  - Estimated query time: <50ms for 10k messages

[CHAT-004] Subscribe to New Messages (WebSocket)
───────────────────────────────────────────────────────────────────────
GraphQL Schema:
  type Subscription {
    messageReceived(conversationId: ID!): Message!
  }

Authentication:
  - Required: userId from WebSocket connection context
  - Validates: userId is participant in conversationId

WebSocket Implementation:
  1. On subscribe:
     - Verify user is participant (same check as CHAT-003)
     - Subscribe to PubSub topic: `MESSAGE_SENT:${conversationId}`
     
  2. On message published (from CHAT-002):
     - PubSub emits to all subscribers of topic
     - Apollo sends Message object to connected clients
     
  3. On unsubscribe:
     - Clean up PubSub subscription

Code Example (resolver):
  messageReceived: {
    subscribe: withFilter(
      (_, __, { pubsub }) => pubsub.asyncIterator(['MESSAGE_SENT']),
      async (payload, variables, context) => {
        // Verify user is participant
        const conv = await db.conversations.findOne({
          _id: ObjectId(variables.conversationId),
          participant_ids: context.userId
        })
        return conv && payload.conversationId === variables.conversationId
      }
    )
  }

Business Logic:
  - Only participants receive messages
  - Subscription established before message sent (no race condition)
  - Client receives own sent messages (for multi-device sync)

Error Handling:
  - 401: WebSocket connection not authenticated
  - 403: User not participant in conversation
  - Connection drops handled by client reconnection logic

Acceptance Criteria:
  ✓ Real-time message delivery to both participants
  ✓ Non-participants cannot subscribe
  ✓ Sender receives own message (confirmation)
  ✓ Handles concurrent messages correctly

Security:
  - Authorization checked on every subscription
  - Cannot subscribe to arbitrary conversations

[CHAT-008] Update Last Online (Heartbeat)
───────────────────────────────────────────────────────────────────────
GraphQL Schema:
  type Mutation {
    updateLastOnline: User!
  }
  
  type User {
    id: ID!
    lastOnline: DateTime!
  }

Authentication:
  - Required: userId from context

MongoDB Operations:
  const lastUpdate = await redis.get(`last_online:${userId}`)
  if (!lastUpdate || Date.now() - lastUpdate > 60000) { // Debounce for 1 minute
    await db.users.updateOne(
      { _id: userId },
      { 
        $set: { last_online: new Date() },
        $setOnInsert: { _id: userId }
      },
      { upsert: true }
    )
    await redis.set(`last_online:${userId}`, Date.now(), 'EX', 300) // Update Redis, expire in 5 min
  }

WebSocket Event:
  - Publish to: `USER_STATUS_CHANGED:${userId}`
  - Payload: { userId, lastOnline }
  - Purpose: Update "Active now" status for other users

Business Logic:
  - Called periodically from frontend (heartbeat)
  - Creates user document if doesn't exist (first-time chat user)
  - Upsert ensures no error if user not in MongoDB yet
  - Debounced to reduce database write load

Error Handling:
  - 401: User not authenticated
  - 500: Database write failure (log, don't throw)

Acceptance Criteria:
  ✓ Updates last_online timestamp
  ✓ Creates user document if missing (upsert)
  ✓ Debounced to reduce write load
  ✓ Broadcasts status change

Business Logic:

  - Backend just broadcasts events
  - No historical record of typing events
  - Max 1 typing event per 500ms per user (rate limit on mutation)

Error Handling:
  - 401: User not authenticated
  - 403: User not participant
  - WebSocket disconnection auto-stops typing indicator

Acceptance Criteria:
  ✓ Real-time typing status delivery
  ✓ User does not see own typing indicator
  ✓ No database writes (memory-only)
  ✓ Properly cleans up on disconnect

Performance:
  - PubSub must handle burst traffic
  - Rate limiting on `setTyping` mutation (e.g., max 1 event per 500ms)

  type Mutation {
    addReaction(
      messageId: ID!
      reactionType: Int!

  }

    userId: String!

  }

Authentication:
  - Required: userId from context
  - Validates: userId is participant in message's conversation

MongoDB Operations:

     const msg = await db.messages.findOne({ _id: ObjectId(messageId) })
     const conv = await db.conversations.findOne({
       _id: msg.conversation_id,
       participant_ids: userId
     })
     if (!msg || !conv) throw new Error("Message or conversation not found, or unauthorized")

     await db.messages.updateOne(
       { _id: ObjectId(messageId) },
       [{ $set: {
         reactions: {
           $concatArrays: [
             { $filter: {
               input: "$reactions",
               cond: { $ne: ["$this.user_id", userId] }
             }},

           ]
         }
       }}]

  - reactionType must be within defined range (1-6)

Error Handling:
  - 401: User not authenticated
  - 403: User not participant
  - 400: Invalid reactionType (not in range 1-6)
  - 404: Message not found

Acceptance Criteria:
  ✓ Adds reaction to message
  ✓ Replaces existing reaction if user already reacted
  ✓ Validates reaction type range
  ✓ Broadcasts update in real-time
  ✓ Only participants can react

      }
    )
  }

[CHAT-019] Forward Message
───────────────────────────────────────────────────────────────────────
GraphQL Schema:
  type Mutation {
    forwardMessage(
      messageId: ID!
      toConversationId: ID!
    ): Message!
  }

Authentication:
  - Required: userId from context
  - Validates: 
    * userId is participant in source conversation (of messageId)
    * userId is participant in target conversation (toConversationId)

MongoDB Operations:
  1. Fetch original message:
     const originalMsg = await db.messages.findOne({
       _id: ObjectId(messageId)
     })
     if (!originalMsg) throw new Error("Original message not found")
     
  2. Verify user is participant in both conversations:
     const sourceConv = await db.conversations.findOne({
       _id: originalMsg.conversation_id,
       participant_ids: userId
     })
     const targetConv = await db.conversations.findOne({
       _id: ObjectId(toConversationId),
       participant_ids: userId
     })
     if (!sourceConv || !targetConv) throw new Error("Unauthorized to forward message to/from these conversations")

  3. Check for unsent message:
     if (originalMsg.meta.is_unsent) throw new Error("Cannot forward unsent message")
     
  4. Create new message in target conversation:
     const recipientId = targetConv.participant_ids.find(id => id !== userId) // Recipient in the target conversation
     
     await db.messages.insertOne({
       conversation_id: ObjectId(toConversationId),
       sender_id: userId, // Current user, NOT original sender
       recipient_id: recipientId,
       content: originalMsg.content, // Copy content only
       time_sent: new Date(),
       meta: {
         is_unsent: false,
         is_forwarded: true, // Mark as forwarded
         reply_to: null, // Don't copy reply reference
         last_edit_at: null
       },
       reactions: [] // Don't copy reactions
     })
     
  5. Update target conversation's last_message
  6. Publish to MESSAGE_SENT for target conversation

Business Logic:
  - Content copied but metadata (senderId, replyTo, reactions) reset
  - Original sender info NOT preserved
  - Frontend displays: "🔄 Forwarded" badge
  - Can forward to multiple conversations (client calls mutation multiple times)
  - Cannot forward unsent messages

Error Handling:
  - 401: User not authenticated
  - 403: User not participant in source or target conversation
  - 400: Cannot forward unsent message
  - 404: Message or conversation not found

Acceptance Criteria:
  ✓ Creates new message in target conversation
  ✓ Sets is_forwarded flag
  ✓ Does NOT copy original sender info, reactions, or reply-to
  ✓ User must be participant in both conversations
  ✓ Broadcasts like regular message
